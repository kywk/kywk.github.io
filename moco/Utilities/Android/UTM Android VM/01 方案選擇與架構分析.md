# 方案選擇與架構分析

要在 Mac 上跑 Android，「主機是 Intel 還是 Apple Silicon」直接決定哪條路走得通。本篇是選型比較；各路線實作見後面文章。

## 需求

長期可用的 Android 環境、Pixel 系 ROM（而非只有 AOSP）、無限空間 Google 相簿。三個條件疊起來，選項很少。

## 關鍵前提：客體架構必須等於主機架構

UTM 底層是 QEMU。只有**客體架構＝主機架構**時才能用 HVF 硬體虛擬化，否則只能用 TCG 模擬（極慢）：

| 主機 | 可原生虛擬化（HVF） | 只能模擬（TCG，很慢） |
| --- | --- | --- |
| Intel Mac | x86_64 客體 | aarch64 客體 |
| Apple Silicon | aarch64 客體 | x86_64 客體 |

因此：

- **Intel Mac**：x86_64 客體（BlissOS / Android-x86）。
- **Apple Silicon**：aarch64 客體（LineageOS virtio 虛擬機 + GSI）。

## 四條技術路線

### 1. 官方 Android Emulator（AVD）

官方映像提供 AOSP / Google APIs / Play Store 版本，適合開發除錯；Emulator 也有 `-system` 可指定外部 system 映像。不過在這次 Apple Silicon、Android 16 ARM64 AVD 的實測中，直接替換成 PixelOS raw GSI 會在 Android 第一階段掛載時失敗，無法取得 ADB。這條低改造路線目前不適合當作可用的 PixelOS 環境；測試過程與限制見 [[06 Android Emulator 與 PixelOS GSI PoC 失敗記錄]]。

### 2. UTM / QEMU 虛擬機

本系列使用的 UTM 路線是 x86 掛 BlissOS，或 arm64 掛 LineageOS virtio 虛擬機再開 GSI。它提供了與上述 Emulator AVD 不同的開機流程；代價是設定繁瑣、映像多為社群維護。

### 3. Linux 容器（Waydroid）

macOS 下要先開 Linux VM 再巢狀執行，且映像是 LineageOS 系、非 Pixel 系。在純 macOS 上不順路。

### 4. 實體手機

使用符合 Google 優惠條件的實體 Pixel，是官方文件明列的路線；仍需依型號、備份畫質與當時規則確認。

## ROM 選擇

| ROM | 現況 |
| --- | --- |
| BlissOS / Android-x86 | x86 專用，適合 x86 虛擬機 |
| PixelExperience | **已停更**（最後 Android 13） |
| PixelOS | 持續維護，有 arm64 GSI |
| LineageOS | 提供 `virtio_*` 虛擬機目標，可當 GSI 宿主 |

PixelExperience 停更後，arm64 的「Pixel 系 ROM」實際上就是 **PixelOS GSI**。

## 什麼是 GSI

只含 **system 分割區**的通用映像，不含 kernel 與 vendor；需宿主提供 kernel/vendor HAL/fstab。arm64 路線就是「LineageOS 虛擬機（宿主）＋ PixelOS GSI（system）」，開機選單有「Boot GSI from /dev/block/vdc」。細節見 [[03 arm64 方案：PixelOS GSI 虛擬機]]。

## 無限空間 Google 相簿的來源

Google 官方保留 2016 年第一代 Pixel / Pixel XL 的**原始畫質**無限備份優惠；這不代表同一帳號在所有裝置上傳都不計容量。本次 PixelOS GSI 帶有 Pixel 2016 feature，並有針對 Google 相簿的裝置身分模擬，但仍需通過 Google 服務啟動與實際備份驗證。

2026-09-30 在 UTM 套用 Samsung Tab S7+ 身分並重設 Google 服務資料後，商店與相簿恢復開啟，相簿初始頁顯示原始畫質、不計配額；**帳號重新驗證、實際上傳與重開機後穩定性尚未完成**。資格與驗證見 [[05 無限空間 Google 相簿]]，操作記錄見 [[07 Play Protect 排錯與裝置身分模擬]]。
